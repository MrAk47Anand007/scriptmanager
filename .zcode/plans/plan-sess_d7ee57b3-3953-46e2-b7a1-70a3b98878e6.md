━━━ PHASE 4 — WORKFLOW ENGINE POWER ━━━
4.1 New node types: foreach, sub-workflow, try/catch
- foreach: config {items (mapping-resolved array), maxIterations clamp 1-100, itemVariable}. Execution: materialize iterations — for i in items: run downstream? No — foreach holds a body: child nodes are the subgraph following its `loop` port. Simpler v1: foreach node executes an inline body = the single next-layer chain until a `join`-marked node? Too complex — choose: foreach config has `steps` sub-definition (mini definition with its own nodes/edges); execute per item with item injected into context ({{items.item}}), aggregate outputs {iterations: n, results: [...]}. Node runs recorded as workflow_node_runs rows with node_id "foreachId#1", "#2". validate: body graph acyclic, depth ≤ 1 (no nested foreach in v1).
- sub_workflow: config {workflowId}; runs start_workflow_run_record, polls to completion (cancel-aware), output = child run summary; depth cap 5 via run input flag; cycle guard via ancestry list in input.
- try/catch: node type 'try' with two ports success/failure: runs its body (sub-definition like foreach); downstream `catch` edge (sourcePort 'error') activates on body failure; failurePolicy interplay documented.
- Frontend: nodeRegistry entries + inspector fields (JSON textarea for items, workflow picker for sub-workflow); templates updated.
- Tests: foreach aggregate outputs + cancel mid-loop; subworkflow depth cap; try routes error port on failure and success port otherwise.

4.2 Debugging + live run events
